# Backend design

The backend is a modular monolith following the reference's layered package structure. Controllers accept validated request DTOs and return response DTOs. Services enforce ownership and business rules. Repositories persist metadata, and infrastructure adapters handle object storage and calls to OCR. Use direct constructor injection and interfaces only for actual replaceable boundaries.

Identity, subjects and document metadata are now implemented. Registration stores a BCrypt password hash; login issues a signed 12-hour HS256 bearer token whose subject is the user's UUID. The signing secret comes from `APP_JWT_SECRET` and must be at least 32 UTF-8 bytes. Protected routes derive ownership only from the verified token. An inaccessible subject or document returns 404, including when another user owns the identifier. A subject cannot be deleted while a document refers to it. General documents have no subject; academic documents reference a subject owned by the same user. The database also enforces that relationship with a composite foreign key.

The HTTP layer follows the reference backend's relevant conventions: annotated OpenAPI operations and bearer security, validated request DTOs, stable error codes paired with HTTP statuses, one error envelope for MVC and security failures, and a request correlation ID in responses and logs. Service interfaces and a separate identity provider are deferred because there is only one service implementation and self-issued tokens satisfy the current MVP scope.

Each business failure has a dedicated exception class extending `BusinessException`; the base carries its stable `ErrorCode` for localized handling. Request and security failures use their corresponding Spring exceptions and are mapped by the same handler or the security response writer. This keeps service code independent of HTTP status and message text.

Java packages use `com.stac.documentdigitization`. Request and response type names end in `Dto`; dedicated mappers convert entities to response DTOs. Lombok generates constructor injection and JPA getters, while the multi-field error envelope uses a builder. Localized English and French messages live in `i18n/messages*.properties`; English is the default and fallback.

Original page images are stored in a private MinIO bucket under server-generated keys. Uploads validate actual JPEG/PNG content, size and dimensions before storage. Page mutations lock the owned document row; reorder requests must contain every current page ID exactly once, and positions are persisted in PostgreSQL. A deletion queue survives MinIO outages and retries object removal after page or document metadata is deleted. Upload rollback queues attempted keys for cleanup. Conversion jobs remain next: job creation will capture page order, a bounded worker will claim persisted jobs, and downloads will resolve an export through an owned document.

Liquibase owns schema changes; Hibernate validates the schema. Migration V1 creates users, subjects and documents with ownership constraints and indexes; V2 adds pages and the object deletion queue. Each later feature will add a versioned changeset alongside its entity and tests. The current token flow has no refresh or server-side revocation; the frontend must discard its token on logout. Shorter token lifetimes or revocation can be added when the product requires them.
